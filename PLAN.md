## Working rules and definition of done

Statuses are READY, PLANNED, IN_PROGRESS, BLOCKED, DONE and DEFERRED. Assign an owner on start. Completion records commit/PR, exact SDK package version/hash and contract revision, commands/results, tested runtime/transport, reports and documentation. Record a blocker explicitly; do not confuse dependencies with a runtime failure.

- Applications consume installed tarballs/wheels or released packages through public APIs. Do not rely on npm link, editable Python installs, sibling source imports, relative workspace schema paths or hidden development tooling for acceptance.
- Reference code contains business/application wiring and generation strategy; contract resolution/validation/negotiation comes from the SDK. Deliberately malformed peer fixtures may handcraft wire payloads to test rejection.
- A clean checkout must reproduce documented scenarios with declared runtimes and supplied artifacts. Servers use configurable ports, readiness signals and reliable cleanup, not arbitrary sleep delays.
- Normal demonstrations run without cloud accounts, paid APIs or model credentials. Optional generation is isolated and its availability/limits are stated.
- Every scenario documents expected results, failure code/state and execution/publication expectations. Logs/reports redact values and secrets by default.
- Formatting, lint/type checks, deterministic transport tests, documented commands and artifact-install tests pass. No required checks are skipped.
- A conformance report states the exact supported profile. Passing reference scenarios is evidence toward conformance, not a blanket assertion about all dialects/transports.
- Update this plan and the root milestone when evidence changes. Future GitHub issues can use the same task IDs.

## REF-001: Reproducible Node package-consumer harness

Outcome: an isolated, repeatable environment that proves the Node SDK artifact works outside its own repository.

Acceptance criteria:

- Define artifact input/version/hash configuration and install the npm tarball through public package tooling. Support released versions later without changing application imports.
- Build a configurable local agent launcher and client runner using SDK public APIs. Provide readiness/health signals, dynamic test ports, process timeouts and guaranteed shutdown on success, failure and cancellation.
- Establish reproducible dependencies and formatting/lint/type/test commands. Plain JavaScript import use and compiled TypeScript application use are both exercised.
- Provide a language-neutral scenario/result manifest and initial CI artifact-consumer smoke test; expected outputs are owned by the reference scenarios, not generated by the SDK implementation under test.
- Prove a fresh isolated consumer can discover the advertised extension and invoke one versioned inline JSON contract. No source checkout or public schema download is necessary for normal execution.
- Document setup, artifact selection, launch/invoke/cleanup commands and expected output. Record actual package/contract/runtime versions.

Evidence: Not started.

## REF-002: Complete deterministic Node reference scenarios

Outcome: a useful set of complete clients and agents showing the entire inline contract profile.

Acceptance criteria:

- Implement a deterministic JSON-to-JSON application using a domain contract owned by the reference repository and an unknown-to-client schema discovered from the Agent Card. Business execution must be distinguishable from validation for test evidence.
- Add text-to-JSON, JSON-to-text and schemaless cases, plus required/optional/none input/output combinations supported by the SDK. Explicitly exercise JSON null/empty values versus absence.
- Include multiple contracts/representations, client selection and A2A accepted-output media negotiation. Demonstrate primary Parts alongside companion text/data without accidentally validating companions.
- Demonstrate valid no-input companion carriers and completed no-output Tasks. Use versioned contract IDs and the pinned extension URI; never invent empty Messages or Artifacts.
- Exercise allowed status/companion streaming with atomic contracted output, task correlation and a continuation case where supported. Run entirely through installed public SDK APIs.
- Supply a tutorial explaining the wire flow and compact request/result examples. Each scenario has a repeatable command and automated assertions about data, metadata and final state.

Evidence: Not started.

## REF-003: Node protocol, failure and security demonstrations

Outcome: external evidence that SDK guarantees remain true across a real transport boundary.

Acceptance criteria:

- Send invalid input directly over transport so client-side validation cannot mask server validation. Prove the wrapped business executor/side-effect counter remains unchanged.
- Trigger invalid generated output and verify the client receives a documented failure without an already-published successful contracted result. Include stream/terminal races and bounded buffering cases.
- Add a deliberately nonconforming peer to demonstrate independent client rejection of missing/conflicting primary metadata, incorrect result echoes, schema-invalid output and invalid carriers.
- Exercise unknown contracts/representations, version mismatches, absent required activation, optional-extension baseline behavior and no mutually supported output. Match spec error/state semantics rather than validator-specific wording.
- Demonstrate allowed external catalog/schema discovery against a controlled test HTTPS service with an explicitly configured test policy. Negative scenarios cover prohibited addresses/redirects, integrity mismatch, unavailable resources and exceeded limits.
- Validate cancellation, timeout, shutdown, concurrent-request separation, secret/error redaction and no leaked child processes/sockets.
- Produce structured, sanitized scenario reports and explain how to diagnose each failure. SDK fixes belong in the SDK repository; reference code must not work around a broken library.

Evidence: Not started.

## REF-004: Node developer/operations guide and validation report

Outcome: an unfamiliar developer can install, run, integrate and troubleshoot the Node implementation.

Acceptance criteria:

- Deliver a verified quickstart, scenario catalog, flow explanation, SDK integration guide, configuration/environment reference, expected errors and troubleshooting with exact commands.
- Include a deployment-style recipe with readiness, graceful shutdown, configurable hosts/ports, request/resolver limits and optional diagnostics. If containers are supplied, test built-artifact installation, runtime limits and non-root operation; containers are optional for the local quickstart.
- Document authentication/context pass-through, administrator resolver allowlisting and credential ownership without shipping real credentials. Separate application/domain assumptions from extension behavior.
- Run the entire inline and first-release scenario set against exact SDK artifacts on declared Node versions, plus portability smoke tests for claimed operating systems.
- Store reports referencing artifact hashes, source revisions and profile requirements. No undocumented manual source edits should be necessary to reproduce the validation.
- Provide the independent Node acceptance evidence consumed by SDK-008 and root milestone M3. Unimplemented profile requirements remain visible rather than being renamed as successful demonstrations.

Evidence: Not started.

## REF-005: Complete Python reference applications

Outcome: independently written Python clients and agents reproduce the accepted Node scenarios.

Acceptance criteria:

- Install a built SDK wheel into an isolated environment; public imports/resources work without editable installation, SDK source or workspace inputs.
- Implement idiomatic typed/async Python applications using the same domain contracts and scenario manifests. Keep missing/null semantics explicit and lifecycle/resource ownership clear.
- Cover the same deterministic input/output/media/presence/continuation/streaming and external-resolution cases as Node, including direct invalid-input and invalid-output demonstrations.
- Verify client validation against the malformed peer and server non-execution/non-publication guarantees. Preserve documented error codes and core state semantics.
- Add interpreter-matrix checks, formatting/lint/type checks, process readiness/timeout/cleanup and cross-platform smoke coverage for supported platforms.
- Deliver executable Python setup, quickstart, scenario, operations and troubleshooting documentation. Record actual installed wheel hashes and supported runtime/SDK versions.

Evidence: Not started.

## REF-006: Four-pairing interoperability and parity suite

Outcome: interoperable behavior is demonstrated independently of either implementation language.

Acceptance criteria:

- Run JS→JS, Python→Python, JS→Python and Python→JS clients/servers against exact installed artifacts, the same pinned extension and the same versioned domain contracts.
- Compare semantic results: acceptance/refusal, selected representation, primary metadata, presence, result identity, final state and side-effect/publication timing. Error prose and JSON object key order need not match.
- Include object/Boolean schemas, missing/null/empty values, supported numeric limits, regex/format vocabularies, companion Parts, negotiation, external dependencies/integrity, streaming and cancellation.
- Include adversarial shared fixtures and generated cases with independently specified invariants. Correct implementation discrepancies rather than changing expected outcomes to fit a language.
- Prevent false passes from source imports, reused servers/state, skipped pairings, transient-port races or uncontrolled internet dependencies. Report each pairing and required scenario separately.
- Produce a requirements-linked parity report and documented commands to reproduce failures. Differences outside the selected profile are explicit unsupported cases, not silent fallbacks.
- Provide evidence for SDK-012 and root milestone M4. If a common draft ambiguity emerges, document it and propose a specification change separately.

Evidence: Not started.

## REF-007: Schema-driven generation demonstration

Outcome: show how a client can construct valid input from a newly discovered schema using optional generation.

Acceptance criteria:

- Provide a documented generator interface that receives the discovered input schema and user/application intent, returns a candidate payload and uses the SDK's normal validation/invocation path.
- Include deterministic code-driven construction and an optional real LLM/provider integration chosen after provider-specific research. Keep model credentials and heavy dependencies out of normal package/scenario paths.
- Handle a provider's supported schema subset explicitly. Unsupported generation features are reported; the original full boundary schema remains authoritative.
- Demonstrate bounded repair/retry on candidate-validation failure, failure exhaustion, error redaction and zero server dispatch until valid input exists. Do not turn generation retries into automatic retries of side-effecting A2A calls.
- Use deterministic test doubles for mandatory CI and document separately which behavior has been validated with a real provider/model. A mock result must never be reported as live-model evidence.
- Deliver a runnable tutorial and limitations for discovered-schema construction. Do not claim that any arbitrary schema or natural-language prompt can always be satisfied.

Evidence: Deferred; optional demonstration, not a prerequisite for deterministic package readiness.

## REF-008: Cross-repository CI and joint reference readiness

Outcome: the reference repository continuously validates shipped SDK artifacts with reproducible, useful reports.

Acceptance criteria:

- Configure cross-repository artifact intake by explicit version/revision/hash. Offline local-artifact mode works before remote repositories exist; remote setup is recorded when actually available.
- Run a fast Node/reference gate for SDK candidates and the full four-pairing suite for joint candidates. Install built distributions into fresh consumers and retain sanitized reports/artifact provenance.
- Establish least-privilege workflows, reviewed dependencies, deterministic scenario environments, supported runtime/OS matrices and bounded job/process timeouts.
- Consolidate Node/Python quickstarts, configuration/operations guidance, package/contract compatibility matrix, contribution guide, changelog/release mapping and security-reporting policy.
- Verify every supported tutorial/command and deployment recipe against installed artifacts. Normal scenarios remain reproducible without external accounts; optional generator checks are clearly separate.
- Tie the reference revision to SDK release candidates and produce a root M5 readiness report with exclusions and reproduction commands. Preparing workflows does not mean GitHub/PyPI/npm publication has happened.

Evidence: Not started.

## REF-009: Bundle and XML/XSD reference coverage

Outcome: demonstrate the later delivery formats/dialects through the same package-consumer boundary.

Acceptance criteria:

- Add versioned JSON Schema bundle and selected XML/XSD domain contracts using SDK-014/SDK-015 capabilities through public APIs.
- Cover allowed entrypoint/include/import resolution and integrity, plus traversal, archive limits, entity expansion, prohibited dependencies and malformed/invalid output.
- Run supported cross-language pairings from built artifacts and compare semantic outcomes. Include platform/runtime installation evidence for any native validator requirements.
- Document large-schema deployment, resolver configuration, limits, dependency graphs and troubleshooting. Avoid unlicensed domain schema redistribution.
- Expand the scenario/support/conformance reports only for validated capabilities and retain the first-release exclusions/history.

Evidence: Deferred; waits for complete bundle/XML SDK support.
